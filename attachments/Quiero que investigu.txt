# 2. Restricción crítica: el despliegue a Store es un RELEASE, no CI normal

**Microsoft Store NO debe recibir ninguna publicación por un PR ni por un push normal a una rama.**

Los commits ordinarios, fixes pequeños, documentación, refactors, merges a `main`, etc. NO deben iniciar una submission de Microsoft Store.

El deployment a producción debe suceder únicamente como consecuencia de un **lanzamiento formal de versión**.

Para GitHub Releases, investiga y utiliza preferentemente una semántica equivalente a:

`release -> published`

y asegúrate además de distinguir correctamente:

* draft releases;
* prereleases;
* releases estables.

Por defecto, **solo una release estable publicada debe poder desplegar a Microsoft Store**.

No utilices como trigger de producción:

* `pull_request`;
* `push` de `main`;
* `push` de cualquier otra rama;
* cambios de archivos mediante `paths`;
* un simple commit.

Evita también utilizar un mero `push` de tag como sustituto de una release publicada si el repositorio ya dispone de un concepto formal de GitHub Release.

Puede utilizarse `workflow_call` para reutilización interna.

Un `workflow_dispatch` manual solo puede existir si tiene una justificación clara como mecanismo de recuperación administrativa, nunca como camino normal de publicación, y debe quedar debidamente protegido contra publicaciones accidentales.

# 5. Garantiza la procedencia exacta del código publicado

Una release de Microsoft Store debe corresponder **exactamente al tag/commit de la release**.

Nunca construyas accidentalmente desde el HEAD actual de `main`.

El checkout del pipeline de Store debe utilizar explícitamente el ref/tag/commit correspondiente a la release que disparó el workflow.

Valida como mínimo:

* tag;
* SHA;
* versión declarada;
* versión del paquete;
* artefacto generado.

Todos deben representar la misma release.

No permitas publicar un binario creado desde un commit diferente al de la release.

`Package Identity Version / versión enviada a Microsoft Store`.

# 16. Idempotencia

* reintentos manuales;

* fallo después del upload pero antes de finalizar;

No utilices simplemente `cancel-in-progress: true` si cancelar una submission parcialmente ejecutada pudiera dejar estado inconsistente; analiza cuál es la política correcta.
